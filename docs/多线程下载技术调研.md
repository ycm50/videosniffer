# 多线程下载开源仓库技术调研

> 调研日期：2026-08-03
> 背景：hanime1 Android 项目，视频源为 HLS 流媒体，需实现多线程断点续传下载。
>
> **落地情况（v1.1）**：分片区间计算、Range 断点续传、任务级限流、状态机均已按本调研实现。
> 实现细节见 [App设计方案.md](App设计方案.md)；对应代码：`download/ShardCalculator.kt`、
> `download/engine/SingleFileDownloader.kt`、`download/hls/`、`download/DownloadManager.kt`。
>
> 与调研建议的差异：
> - 并发控制用**协程 + Semaphore**，未自建 `ThreadPoolExecutor` 双池（见 `DownloadManager` 说明）；
> - 分片写入用 `RandomAccessFile("rw")` 而非调研建议的 `"rwd"` —— `rwd` 每次写同步落盘会序列化
>   多线程磁盘 IO，实测吞吐大幅下降；
> - m3u8 合并未引入 ffmpeg：AES-128 用 `javax.crypto` 解密，MPEG-TS 字节级 concat；
>   fMP4 流额外拼接 `#EXT-X-MAP` 初始化段。**`SAMPLE-AES` 暂不支持，会显式报错而非产出损坏文件。**

## 2. 核心流程

### 2.1 探测阶段（Probe）— 决定单线程还是多线程

`Aspsine` 的 `ConnectTaskImpl` 先发送 `Range: bytes=0-` 请求探测服务器支持：

- 返回 **206 (HTTP_PARTIAL)** → 支持 Range → 多线程下载
- 返回 **200 (HTTP_OK)** → 不支持 Range → 回退单线程
- `devaige` 的 `DLTask` 额外处理：
  - 重定向：`HTTP_MOVED_PERM/TEMP`、`HTTP_SEE_OTHER`、`HTTP_NOT_MODIFIED`、`HTTP_TEMP_REDIRECT`，最多 `MAX_REDIRECTS` 次，重定向后更新 `realUrl`
  - `Transfer-Encoding: chunked` 时无法获知总大小 → 走单线程
  - `Content-Length` 解析失败（负数）→ 视为不可断点下载

### 2.2 分片区间计算

`Aspsine`（`DownloaderImpl.getMultiThreadInfos`）：

```java
long average = length / threadNum;
long start = average * i;
long end = (i == threadNum - 1) ? length : start + average - 1; // 最后一片吃到文件尾
```

`devaige` 按固定每线程字节数 `LENGTH_PER_THREAD` 切分：

```java
if (totalBytes <= LENGTH_PER_THREAD) {
    threadSize = 2;
    threadLength = totalBytes / threadSize;
} else {
    threadSize = totalBytes / LENGTH_PER_THREAD;
}
// 每线程 [start, end]，最后一线程吃余数 remainder
```

### 2.3 Range 请求与断点续传

```java
// 关键：当前线程已下载的 offset 加到 start 上
long start = threadInfo.getStart() + threadInfo.getFinished();
headers.put("Range", "bytes=" + start + "-" + end);
```

每个线程只写自己独立的区段，配合 `RandomAccessFile` 实现并发安全写入。

### 2.4 并发文件写入

- 每个线程打开 `RandomAccessFile(file, "rwd")`（rwd = 每次写入同步到磁盘，防断电丢失）
- `raf.seek(start)` 定位到该线程起始偏移
- 各线程写互不重叠的字节区间，无需加锁
- 回退单线程时用普通 `FileOutputStream`，不落数据库

### 2.5 断点续传持久化（SQLite）

线程表结构（devaige 与 Aspsine 基本一致）：

```sql
CREATE TABLE ThreadInfo (
  _id INTEGER PRIMARY KEY AUTOINCREMENT,
  id INTEGER,      -- 线程序号
  tag TEXT,        -- 任务标识（通常为 url 的 hash）
  uri TEXT,        -- 下载地址
  start LONG,      -- 区间起点
  end LONG,        -- 区间终点
  finished LONG    -- 已下载字节数
);
```

生命周期：

| 事件 | 动作 |
|---|---|
| 任务开始 | 插入各线程区间记录 |
| 下载中 | 定期 `UPDATE ... SET finished=? WHERE tag=? AND id=?` |
| 线程完成 | 删除该线程记录 |
| 任务完成 | 删除整条任务记录 |
| 暂停/停止 | 保留记录 → 下次启动复用续传 |
| 取消 | 删除 DB 记录 + 删除本地文件 |

`devaige` 额外有一张任务表 `DLInfo`（含 baseUrl、realUrl、dirPath、fileName、totalBytes、currentBytes、disposition、mimeType），并在内存中维护三类集合：
- `TASK_DLING`（ConcurrentHashMap）：正在下载
- `TASK_PREPARE`（synchronizedList）：超出 maxTask 限流的排队任务
- `TASK_STOPPED`（ConcurrentHashMap）：暂停恢复，先查内存再查 DB

## 3. 线程池与并发控制

### Aspsine

```java
mExecutorService = Executors.newFixedThreadPool(config.getMaxThreadNum()); // 全局共享
// 每个下载任务占用 config.threadNum 条线程
```

### devaige（双线程池）

```java
int CORES = Runtime.getRuntime().availableProcessors();
int POOL_SIZE = CORES + 1;
int POOL_SIZE_MAX = CORES * 2 + 1;

// 任务池：负责 DLTask（连接、分片、调度）
new ThreadPoolExecutor(POOL_SIZE, POOL_SIZE_MAX, 3s, ..., POOL_QUEUE_TASK(56), TASK_FACTORY);
// 下载线程池：5 倍容量，负责 DLThread（实际字节下载）
new ThreadPoolExecutor(POOL_SIZE*5, POOL_SIZE_MAX*5, 1s, ..., POOL_QUEUE_THREAD(256), THREAD_FACTORY);
```

- 线程命名 `DLTask #N` / `DLThread #N` 便于日志定位
- 任务级限流：`setMaxTask(int)`，超过则进排队队列
- 线程内设置 `Process.setThreadPriority(Process.THREAD_PRIORITY_BACKGROUND)`

## 4. 状态机与回调

Aspsine 完整状态链：

```
STARTED → CONNECTING → CONNECTED → PROGRESS → COMPLETED
                                              ├─ PAUSED
                                              ├─ CANCELED
                                              └─ FAILED
```

- 回调通过 `Handler(mainLooper)` 投递到主线程（`DownloadStatusDeliveryImpl`），避免 UI 线程竞争
- `DownloadResponse` 封装状态 + 回调，`DownloadStatusDelivery` 负责线程切换
- `Downloader` 持有多个 `DownloadTask`，只有全部子任务完成/暂停/失败时才对外回调对应状态（`isAllComplete/isAllPaused/isAllFailed/isAllCanceled`）
- 任务去重：`Map<String, Downloader>` keyed by `tag.hashCode()`，重复启动直接拒绝

## 5. M3U8 / HLS 分段下载与合并

`cloudgyb/m3u8-downloader` 状态机：

```
NEW → M3U8_PARSING → M3U8_PARSED → DOWNLOADING → DOWNLOAD_FINISHED → SEGMENT_MERGING → FINISHED
        │                  │              │              │                    │
        └── M3U8_PARSE_FAILED          DOWNLOAD_FAILED     │           SEGMENT_MERGE_FAILED
                                                            └── SEGMENT_MERGED
```

### 流程

1. **解析**：请求 `.m3u8` playlist，解析出所有 `.ts` 片段 URL（含时长 `#EXTINF`）
2. **分段下载**：
   ```java
   ThreadPoolExecutor(cpuCores*10, cpuCores*20, 60s, LinkedBlockingQueue(1000), AbortPolicy)
   ```
   - 每次批量取 `maxThreadCount` 个未完成片段提交线程池
   - 每片段写独立临时文件（`m3u8_{taskId}/{segmentId}.ts`）
   - `Future.get()` 等待本批完成，更新 `finishedMediaSegment/totalMediaSegment` 计算进度
   - 循环直至无剩余片段
3. **合并**：调用 `FfmpegUtil.mergeTS(segments, target, true)` 用 ffmpeg 合并为 `.mp4`
   - 失败状态（DOWNLOAD_FAILED / SEGMENT_MERGE_FAILED）可重新触发任务续跑
   - 手动停止：`AtomicBoolean isStopped` 在每批循环开头检查

### 关键点

- 进度 = `已下载片段数 / 总片段数`
- 片段级断点续传：DB 中每个 segment 记录 `finished` 与 `file_path`，重启任务跳过已完成的
- 每片段 `bytesCounter`（AtomicLong）每秒归零一次，用于计算实时下载速率（`DownloadRateChangeEvent`）

## 6. 对 hanime1 项目的落地方案建议

### 架构选型

采用 **M3U8 分段下载**（方案 3），吸收前两个库的断点续传 DB 设计与状态机：

| 模块 | 方案 |
|---|---|
| HLS 解析 | 自行实现 `.m3u8` parser 或集成 `media3`/`jwplayer` 的 HLS 解析 |
| 线程池 | `ThreadPoolExecutor(cpuCores*2, cpuCores*4, keepAlive, LinkedBlockingQueue)`，Android 上不宜过大 |
| 分段并发 | 每批 N 段并行下载，每段独立临时文件 |
| 合并 | Android 端集成 `ffmpeg-kit`，或直接 MPEG-TS 字节级 concat（多数 `.ts` 可无损拼接，速度快） |
| 断点续传 | SQLite 表：`segments(id, task_id, url, finished, file_path, duration)` + `task(task_id, url, state, total_segments, finished_segments)` |
| 状态管理 | 借鉴 Aspsine 状态机 + Handler 主线程回调 |
| 任务限流 | `ConcurrentHashMap` 去重 + maxTask 排队（借鉴 devaige） |

### 注意事项

- hanime 的 `.m3u8` 多为带 token 的签名 URL，解析后需尽快下载，过期需重新从 API 获取
- 分段下载需关注 Referer / User-Agent / Cookie 等防盗链请求头
- 停止语义区分：暂停保留进度可续传；取消删除进度和临时文件
- 进度上报需节流（devaige 每 1 秒上报一次，避免刷爆主线程）
