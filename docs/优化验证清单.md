## 3. 回归重点（最容易被本轮改坏的地方）

| 场景 | 为什么要注意 |
|---|---|
| 暂停 → 继续 → 取消 → 删除 | DB 改为异步落库，检查状态迁移与持久化是否仍一致（重启 App 后任务仍在） |
| mp4 断点续传 | 分片进度现在会中途落库，检查续传后文件可播放（不是从错误偏移开始） |
| m3u8（AES-128）断点续传 | 已落盘分片复用逻辑未变，但落盘改成了流式写 → 检查成品能播放 |
| 导出 | `MediaStoreExporter` 未改；确认完成后文件出现在 `Download/hanime1/` |
| 单文件无 Range 源 | 走 `downloadFull` 分支，确认仍能下完（该分支只换了 UA 常量） |

## 4. 已知风险与取舍
- **流式解密**：填充错误会在流末尾抛 `IOException`，按「分片失败」重试；若某个源用非标准填充，
  会连续失败 3 次后报错（此前的整段解密同样会失败，行为一致）。
- **ListAdapter**：默认不带 payload，进度变化时整项重绑；如果后续想更省，可给 `DiffUtil` 加 payload
  只更新进度条与文本。
- **断网暂停**：切网有 2 秒宽限期，期间任务可能多试一次请求。
- **UA 跟随桌面开关**：只影响**下载请求**；嗅探与页面解析仍用固定移动 UA（刻意保留，见 `SnifferHttp` 注释）。
- **未做**（本轮明确排除）：m3u8 临时分片目录的自动清理、WebView Cookie 共享给下载器。

### 实机暴露的问题（已修）

1. **断网判「失败」而非「暂停」**：设备常驻 VPN 时，飞行模式下 `activeNetwork` 仍是 VPN 且
   声称有 `NET_CAPABILITY_INTERNET`，纯连接状态判定永远不成立；且分片 3 次重试常在 2 秒宽限期内
   先失败。现改为「连接状态 **或** 网络类错误文本」双判据（`DownloadFailureClassifier`）。
2. `M3U8ParserTest` 的 `../../x.ts` 期望值写错（应为 `/x.ts`，按 RFC 3986）——该断言此前从未执行过。
