> 若某个断言失败，大概率是**测试写的期望值与实现不符**（这些断言是按实现手推的），

静态复查已提前对平了三处「测试期望 vs 实现」的不一致（都改了实现，测试不动）：

| 位置 | 问题 | 修正 |
|---|---|---|
| `Hanime1DownloadParser.qualitySuffixRegex` | 正则 `-\d+p$` **没有捕获组**，而 `qualityFromFileName` 取的是 `groupValues[1]`（真匹配上会抛 `IndexOutOfBoundsException`）；且 `$` 要求紧贴结尾，带 `.mp4` 的文件名永远匹配不到 → 清晰度恒为 null | 改为 `-(\d+)p(?:\.[A-Za-z0-9]{1,5})?$`（补捕获组 + 扩展名可选），`qualityFromFileName` 与 `stripQualitySuffix` 共用 |
| `Hanime1DownloadParser.qualityFromUrl` | 用 `Uri.parse(...).lastPathSegment`，但文档与测试都把它当纯函数 → JVM 单测里 `Uri` 是桩，必失败 | 改为纯字符串取路径末段（`substringBefore('?')/'#'` + `substringAfterLast('/')`） |
| `MediaUrlDetector.itagQualities` | `313` 被标成 `2160p60`（实为 VP9 2160p/30fps，60fps 的是 `315`） | `313 to "2160p"` |

## 5. 已知未覆盖项（非本次范围）

- `SAMPLE-AES` / Widevine 加密流不支持（会显式报错）。
- 下载列表的「顶部聚合栏（总进度/活跃数）」与「状态过滤 Tab」未实现，已在设计文档标注。
- `MediaUrlDetector.isVideoCandidate` 依赖 `android.net.Uri`，单测未覆盖，需仪器测试。
- 直播（无 `#EXT-X-ENDLIST`）的 m3u8 会按当前已解析到的分片下载，不做滚动跟随。
- **YouTube PO Token 无法生成**（需 BotGuard JS）：Route D 对部分视频拿不到直链，属能力边界而非 bug，
  此时靠 Route A（播放时拦截）兜底。
- **YouTube 不引入 JS 引擎**：带 `signatureCipher` 的格式一律放弃（签名还原算法在播放器混淆 JS 里）。
- **不做音视频合流**：YouTube 的 video-only 格式（1080p 以上几乎都是）下下来无声，只做标注不做合成。
- **YouTube 只支持 mp4 容器**：webm/vp9 格式被丢弃，因为导出链路固定 `video/mp4` + `.mp4`。
- **SABR 流**（服务端自适应码率，UMP POST 协议）不支持，按其 `sabr` 参数筛掉。
- `YouTubeParser.matches` / `MediaUrlDetector.isVideoCandidate` / `detect` 依赖 `android.net.Uri`，
  单测未覆盖（已把其中可纯化的逻辑拆出来测），需仪器测试补足。
- **「电脑版网页」只改 WebView 的页面加载**：嗅探解析器（hanime1 下载页抓取、InnerTube 客户端）
  与下载请求仍用各自固定的 UA —— 那些请求靠固定 UA 过防盗链/装作官方客户端，与页面版本无关。
  因此开启后站点呈现桌面版，但「拿到直链」的路径不变。
- **电脑版 UA 是 Windows Chrome**（Chrome 主版本取本机 WebView 真实版本），并非真实桌面浏览器：
  依赖 `Sec-CH-UA` 客户端提示、桌面专属 JS 特性或强制登录的站点仍可能不认。
